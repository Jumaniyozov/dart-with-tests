## 26.1 Decide whose fault it is

Every failure in a program belongs to one of two people.

**The world is awkward.** Someone typed `12.5`, a file is missing, a network is down. Nothing
is wrong with your program — this is the ordinary weather it was written to work in. Failures
like these are **expected**, and something has to do the expecting.

**Your program is wrong.** A negative length, an index past the end, a state that should have
been impossible. Nothing sensible can be done at run time because the mistake was made earlier,
by a programmer.

The rule this study is built on: **expected failures are values; bugs are exceptions.** A value
has to be looked at — the compiler can insist on it. An exception is easy to ignore all the way
up to a stack trace, which is exactly right for a bug and exactly wrong for a typo.

<Gloss title="Why the base has a constructor">
`sealed class const Reading();` looks like it does nothing, and it is load-bearing.

`Understood` and `Unreadable` are `const` classes, and a constant constructor may only call
another constant constructor. Write the base as a bare `sealed class Reading {}` and its
implicit constructor is not `const`, so every subclass fails with *"A constant constructor can't
call a non-constant super constructor"*. Measured while writing this study, on the first
attempt.
</Gloss>

Read the first block again. **`dart run` does not enable asserts.** Neither does the binary from
`dart compile exe`. `half(7)` answered `3` twice, quietly, in the two ways you actually run a
program.

The assert fires in exactly two places: under `dart test`, and under `dart run --enable-asserts`
if you ask for it by name.

So an `assert` is not a weak check. It is a **message to yourself while you are testing**, and
it is absent from the program you ship. That is why `Money.fromPence` throws and does not
assert, and why the check on what a person typed lives in `readMoney` where it will still be
there tomorrow.

<Gloss title="Then what is an assert for?">
Stating something you believe cannot happen, so that a test proves you right.

`Day`'s month check throws, because a wrong month can arrive from a file. But a private helper
that has already been handed a validated month can `assert` it — the assert documents the
assumption, `dart test` enforces it, and nothing is paid for at run time.

If a check must survive into the shipped program, it is not an assert. It is an `if` and a
`throw`, or a value like `Unreadable`.
</Gloss>

## 26.5 The one you must not catch

`Money.fromPence` throws an `ArgumentError`. `ArgumentError` implements `Error`, and that word
is a claim: **an `Error` means the program is wrong.**

So catching one is a contradiction. You would be saying *the code that got here is broken, and I
will now carry on*. Effective Dart puts it plainly, and it is why `readMoney` asks about the sign
itself rather than wrapping the constructor in a `try`.

The version that catches would have worked. Every test would have passed. It would also have
taught the reader that an `ArgumentError` is something you handle, and the next `ArgumentError`
they meet will be a real bug being swallowed.

<Practice source="Effective Dart — Usage" href="https://dart.dev/effective-dart/usage#do-throw-objects-that-implement-error-only-for-programmatic-errors">
**DO throw objects that implement `Error` only for programmatic errors** — and its companion,
**DON'T explicitly catch `Error` or types that implement it**: *"Since an `Error` indicates a bug
in your code, it should unwind the entire callstack, halt the program, and print a stack trace so
you can locate and fix the bug."*

That pair decides the shape of this whole study. If a failure can be caught and handled, it was
never a bug, so it should have been an `Exception` or a value in the first place. If it really is
a bug, catching it hides the one thing that would have told you where it is.

Run `grep -r 'catch (' lib/` in this package and it comes back empty. Every failure is either a
case of `Reading` that the caller must handle, or an `Error` nobody has any business handling.
(A bare `catch` does match — in comments, explaining why there is none.)

Study 20's Practice covers the lints that police the machinery — `empty_catches`,
`use_rethrow_when_possible`, `control_flow_in_finally`. This is the rule that decides whether you
should be reaching for that machinery at all.

## Wrapping up

Decide whose fault a failure is before you decide how to report it. The world being awkward is
expected and belongs in the return type; the program being wrong is a bug and belongs in an
exception that nobody catches.

A `sealed` result type makes the caller handle every case, because the switch stops compiling
when a case is added. A nullable answer leaves that to their memory, and it cannot carry a
reason — which is the difference between `'abc' is not an amount` and
`pence are two digits, and "5" is 1`.

An `assert` does not run in the program you ship, and — measured, not assumed — it does not run
under `dart run` either. It fires under `dart test` and under `dart run --enable-asserts`, and
nowhere else. Treat it as a note to yourself that tests enforce, never as a guard.

Do not catch an `Error`. If catching it was reasonable, it should not have been an `Error`.

Also met: `sealed` with a `const` base constructor, exhaustive switching over a result,
`dart compile exe`, `--enable-asserts`, and a `lib/` with no `catch` in it.
