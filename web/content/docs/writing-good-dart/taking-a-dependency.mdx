`^2.7.0` is a **caret constraint**, and it means *at least 2.7.0, and less than 3.0.0*. Read it
as a bet on somebody else's discipline: they have promised that nothing before 3.0.0 will break
you, and you have agreed to accept whatever they ship inside that range without being asked.

The constraint says what you **allow**. It does not say what you **got** — for that there is
`pubspec.lock`, which `pub` writes and you commit:

<Console>
<include cwd lang="saff-console" meta='title="terminal"'>../code/ch33_expenses/transcripts/lock.txt</include>
</Console>

The version, and a hash of the exact bytes. That is the difference that matters: a teammate
cloning this repository runs `dart pub get` and gets **2.7.0**, not "whatever satisfies
`^2.7.0` today". The constraint is the policy and the lock is the record, and only one of them
is reproducible.

`direct main` is the other half of the entry: it says *this package asked for it*. Run the same
command against **this book's** lockfile and the line reads `transitive` instead, because these
studies share one workspace and `package:test` was already pulling `args` in long before study
33 asked for it. The distinction is not cosmetic, and the Practice at the end of this study is
about exactly what it costs to blur it.

<Gloss title="Two lists, and callers only get one">
`args` went under `dependencies`. `test` and `lints` are under `dev_dependencies`, which
`dart pub add --dev` writes, and the difference is not tidiness: a dev dependency is not
installed for anyone who depends on **you**. Somebody using this package gets `args`, because
`lib/` imports it and their copy would not compile otherwise. They do not get `test`, because
nothing they can reach mentions it.

The rule follows from that: if a file under `lib/` or `bin/` imports it, it is a dependency. If
only your tests and tools do, it is a dev dependency. Study 34 is where being on the other end
of this starts to matter.
</Gloss>

The shape is the same. Study 14's patterns still read the arguments; they read them off
`(command.name, command.rest)` instead of off the raw list, and the flag arrives as

`flag` and `option` are worth noticing. `results['anyway']` also works and is what most

## 33.3 Help that cannot disagree with the parser

Study 24's `usage` was a `const` string sitting next to the code it described. That is a claim
nothing checks. Add a flag, forget the line, and the help is wrong until somebody happens to
read both.

<include cwd lang="dart" meta='title="lib/src/command.dart"'>../code/ch33_expenses/lib/src/command.dart#usage</include>

<include cwd lang="dart" meta='title="test/arguments_test.dart"'>../code/ch33_expenses/test/arguments_test.dart#help</include>

`--anyway`'s help text is written once, on the flag, and appears in the output because the
parser put it there. The two can no longer drift, and a whole class of stale documentation is
gone.

Only a class of it. `ArgParser` models **options**; the words after a command word are a plain
list it has no opinion about, so `add <amount> <category> <note>` is still a hand-written line
that can still rot. Knowing which half your dependency took over is the difference between
trusting it and assuming things about it.

The other half of study 24's promise arrives here too, and one part of it arrives smaller than
it sounds. `-h` works because `--help` was declared with `abbr: 'h'`. `--hel` does not work:
`args` gives you **single-letter abbreviations**, not unique prefixes, and the test above says
so because that is what it does when you run it.

`1` is `refused` and `2` is `misuse`. Study 24 built its whole exit-code lesson on those being
different answers: `add -5 coffee` is a well-formed request for something `Money` forbids, and
a script can retry a misuse and must not retry a refusal.

`package:args` disagrees. A leading `-` is how an option announces itself, so `-5` is read as a
short option that was never declared, and the amount never reaches the code that would have
refused it. There is no setting for this — `ArgParser` takes `allowTrailingOptions` and
`usageLineLength` and nothing else — and it is not about the abbreviations this program
declares, because a parser with no abbreviations at all does the same thing.

<include cwd lang="dart" meta='title="test/command_test.dart"'>../code/ch33_expenses/test/command_test.dart#dash</include>

`--` is the escape, and it is a convention far older than this package: everything after it is a
word, whatever it starts with. So the distinction study 24 taught is still available, and the
reader now has to type two more characters to get it.

That is the honest shape of taking a dependency, and it is worth more than the `--help` was.
You did not get to pick which behaviours came with the code. Somebody else decided what a
leading dash means, they decided it before you arrived, and the only reason you found out is
that the behaviour was pinned by a test. A change like this in code with no tests is discovered
by a user.

<Practice source="Dart lints — depend_on_referenced_packages" href="https://dart.dev/tools/linter-rules/depend_on_referenced_packages">
**"DO depend on referenced packages. When importing a package, add a dependency on it to your
pubspec."** The rule is in `package:lints/core.yaml` 6.1.0, which `recommended.yaml` includes,
so it is enforced here.

It exists because an import can succeed by accident. `args` was already on this machine before
study 33 asked for it — `package:test` depends on it — so deleting the dependency and keeping
the import leaves a program that still compiles:

## Wrapping up

`dart pub add` writes a line in `pubspec.yaml`, and that line is a caret constraint: a range you
allow, and a bet that the author will not break you inside it. `pubspec.lock` records what you
actually got, hash and all, and it is the lock rather than the constraint that makes a build
reproducible on someone else's machine.

A dependency that belongs to `lib/` or `bin/` goes under `dependencies`, because your callers
need it too. One that only your tests reach goes under `dev_dependencies`, and
`depend_on_referenced_packages` is the analyzer noticing when an import is working by accident.

`package:args` replaced a parser three studies had apologised for. A flag is now a flag wherever
it appears, each command has its own options, `--flag=value` and `-f value` and `-fvalue` all
work, and half the help text is generated from the options rather than typed beside them.

The other half of that sentence is the study. `args` does not abbreviate long names, only
single letters. It does not model the words after a command at all. And it reads a leading `-`
as an option, which took away a distinction study 24 had built a lesson on — recovered with
`--`, at the cost of two characters the reader has to know about.

Also met: `dart pub outdated`, `pubspec.lock` as a record rather than a policy, `ArgParser`,
`addCommand`, `addFlag`, `addOption`, `ArgResults`, the typed `flag` and `option` accessors,
`ArgParserException`, and `--` as the end of options.

Study 34 turns this around: everything here is what a version number promised **you**, and the
last study of Book II is about making that promise to somebody else.
