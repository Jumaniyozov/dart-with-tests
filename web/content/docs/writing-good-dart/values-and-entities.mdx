## 25.2 `hashCode` picks the bucket, `==` searches it

`Category` overrides two things, and the second one is the one people forget.

A `Map` does not compare your key against every key it holds — that would be slow. It asks the
key for its `hashCode`, uses that number to pick one **bucket** out of many, and then uses `==`
to search only inside that bucket.

Both halves have to agree. If two objects are equal but hash differently, they go to different
buckets and `==` is never even asked.

Here is the same idea with `hashCode` left out:

```dart title="bin/buckets.dart"
class Sloppy {
  Sloppy(this.name);

  final String name;

  @override
  bool operator ==(Object other) => other is Sloppy && other.name == name;

  @override
  String toString() => name;
}
```

<Gloss title="Object.hash, and why not to invent your own">
`Object.hash(year, month, day)` combines several fields into one hash code. Use it rather than
adding or XOR-ing fields yourself: `a + b` gives the same answer for `(1, 2)` and `(2, 1)`, and
every collision costs a search.

For a single field, delegate — `Category` returns `name.hashCode`, because `String` already
answers this well.
</Gloss>

## 25.3 A thing, or a description of a thing

`Category` is a **value**. Two categories with the same name are not two categories that happen
to match; they are the same category. Values have no identity of their own, and that is why
giving them `==` is right.

`Expense` is an **entity**.

<include cwd lang="dart" meta='title="lib/src/expense.dart"'>../code/ch25_expenses/lib/src/expense.dart#expense</include>

Look at what is missing: no `operator ==`. Buy a coffee for £3.20, then buy another coffee for
£3.20 on the same day. Every field matches. They are still two expenses, and you spent £6.40.

If `Expense` had value equality, `{first, second}` would be a set of one and the second coffee
would vanish. So an `Expense` is equal only to itself, which is what Dart gives you when you
override nothing.

The test to apply to any new type is one question: **if two of these have identical contents,
is that one thing or two?** One thing means a value and `==`. Two things means an entity and
silence.

## 25.4 A day is not an instant

`Expense` carries a `Day`, not a `DateTime`.

<include cwd lang="dart" meta='title="lib/src/day.dart"'>../code/ch25_expenses/lib/src/day.dart#day</include>

`DateTime` is an instant: a point on a timeline, which belongs to a place as much as to a date.
A day is not. The 9th of September is the 9th of September everywhere, and an expense happened
on a day.

Study 30 measures four separate ways `DateTime` gets this wrong. Here is the one that belongs
to this study, because it is about `==`:

<include cwd lang="dart" meta='title="test/values_test.dart"'>../code/ch25_expenses/test/values_test.dart</include>

Read the last group. The local time and the UTC time are **the same instant** — the microsecond
counts match — and `==` says they are not equal. `isAtSameMomentAs` is the one that answers the
question you meant.

And their hash codes are equal anyway. That is legal: unequal objects are allowed to share a
hash code, and every `Map` handles it. But it is a warning about tests. **Equal hash codes are
not evidence of equality.** A test that compares only hash codes has proved nothing, in the same
way study 8's set comparison passed without proving anything about `==`.

## 25.5 Two ways a list escapes

`Store` holds a `List<Expense>` and hands it out. Both directions leak if you let them.

The way out is `List.unmodifiable`, which copies once and returns a list that throws on `add`.
Return `_recorded` itself and callers get the store's own list, and can change what it holds
without the store ever knowing.

The way in is the same problem mirrored, and `Store` does not have it yet only because it takes
expenses one at a time. Challenge 3 has it.

<Practice source="Effective Dart — Design" href="https://dart.dev/effective-dart/design#avoid-defining-custom-equality-for-mutable-classes">
**AVOID defining custom equality for mutable classes.**

The reason is a `Map`. A key is filed in its bucket when you put it in; change a field the
`hashCode` is built from, and the key is now in the wrong bucket. It is still in the map, and
the map can no longer find it — not with `[]`, not with `containsKey`, not with the very object
you used as the key.

Every field of `Category` and `Day` is `final`, so neither can drift out of its bucket. That is
not a coincidence: **immutability is what makes value equality safe**, and a type that wants
`==` should be asked whether it can also be frozen.

Study 15's Practice covers the companion rule — override `hashCode` if you override `==` —
which the `hash_and_equals` lint enforces, and which 25.2 shows failing.
</Practice>

## Wrapping up

Normalise once, in the factory, and there is no un-normalised value anywhere in the program.

A `Map` asks `hashCode` for the bucket and `==` to search it, so the two must agree or equal
keys land apart — one category becomes two rows, nothing throws, and the total is quietly
wrong. `hash_and_equals` catches the omission; nothing catches a `hashCode` that merely
disagrees, so keep it built from the same fields `==` reads.

A value is equal by contents and should be immutable. An entity is equal only to itself, and
`Expense` gets no `==` because two identical coffees are two coffees. Ask the question of every
new type before you write a line of it.

`DateTime` is an instant and a `Day` is not, which is why the domain holds the second one. The
same instant in two zones is not `==` — and their hash codes match anyway, which is the reminder
that equal hashes prove nothing.

Also met: `Object.hash`, `List.unmodifiable`, `isAtSameMomentAs`, `setUp`, and a store that
forgets everything when the program stops — study 28 gives it a file.

Study 26 goes back to `penceFrom` and asks whether `null` was ever an adequate answer.
