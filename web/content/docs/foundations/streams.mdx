## 22.1 Three keywords

<include cwd lang="dart" meta='title="lib/feed.dart"'>../code/ch22_feed/lib/feed.dart#totals</include>

`async*` marks a function that hands back a `Stream`. `yield` puts one value on it and carries
on. `await for` takes one value each time round the loop, pausing the function in between
exactly as study 21's `await` did — and `runningTotalOf` does both at once: a stream in, a
stream out, which is what most real stream code looks like.

None of the three works without the others in place:

```dart title="lib/wrong.dart"
Stream<int> doubled(List<int> pence) {
  for (final amount in pence) {
    yield amount * 2;
  }
}

int total(Stream<int> feed) {
  var sum = 0;
  await for (final amount in feed) {
    sum += amount;
  }
  return sum;
}

Stream<int> onlyLarge(List<int> pence) async* {
  yield pence.where((amount) => amount >= 1000);
}
```

## 22.2 Nothing runs until something listens

<include cwd lang="dart" meta='title="test/feed_test.dart"'>../code/ch22_feed/test/feed_test.dart#lazy</include>

Calling `feedOf` runs *none* of the body — `log` is empty, and the first line of the function is
a `log.add`. This is not a small print in the API. It is the same laziness study 12 found in
`map` and `where`, and it is why a stream that nobody listens to costs nothing.

The two generator keywords are the same idea twice:

<include cwd lang="dart" meta='title="lib/feed.dart"'>../code/ch22_feed/lib/feed.dart#sync</include>

`sync*` hands back an `Iterable` and pauses at each `yield` until the caller asks for the next
value. `async*` hands back a `Stream` and can also pause at an `await` while it waits for
something. One star, one letter, two studies apart.

## 22.4 One listen, and it is going past whether you are ready or not

This is the part of streams that catches everybody, and dart.dev states it plainly: a
single-subscription stream "can only be listened to once."

The total printed. The second question was not a wrong answer, it was a `StateError` — because
the values are gone. A `List` is a place where values are kept; a `Stream` is not, and asking
it twice is asking for something it never had.

The usual reflex is `asBroadcastStream()`, which allows many listeners. Read what it actually
gives you:

<include cwd lang="dart" meta='title="test/feed_test.dart"'>../code/ch22_feed/test/feed_test.dart#once</include>

The second total is **zero**. Not a `StateError` — a wrong answer, quietly. A broadcast stream
does not keep anything either; it sends each value to whoever is listening at that moment, and
by the time the second listener arrived the till had finished. dart.dev warns about exactly
this: you end up "missing out on initial events, and then the rest of the stream makes no
sense."

So `asBroadcastStream` fixes the exception and not the problem. When you need the values twice,
`await stream.toList()` once and use the list — a `List` is the tool for going round twice.
When you need two answers, get both in one pass, which is challenge 3.

## 22.5 A failure in the middle

<include cwd lang="dart" meta='title="lib/feed.dart"'>../code/ch22_feed/lib/feed.dart#fault</include>

<include cwd lang="dart" meta='title="lib/feed.dart"'>../code/ch22_feed/lib/feed.dart#trouble</include>

<include cwd lang="dart" meta='title="test/feed_test.dart"'>../code/ch22_feed/test/feed_test.dart#trouble</include>

Study 20's `try` and `on` work here with nothing added, for the reason study 21 gave: the
failure arrives at the point where you were waiting. dart.dev is precise about what it costs —
"when reading events using an `await for` loop, the error is thrown by the loop statement. This
ends the loop, as well."

**The loop ends.** Not the value — the loop. `totalUntilFault` keeps the 950 it had counted, and
the `1000` behind the fault is never seen, because there is no way to ask the stream to carry on
from there. If a feed should survive a bad value, the survival has to be built inside the
generator, before the value is ever sent.

<Practice source="dart.dev — Asynchronous programming: Streams" href="https://dart.dev/libraries/async/using-streams">
No lint in `package:lints` has anything to say about streams, so this one is a habit rather than
a rule the analyzer will enforce.

**Decide who owns the stream, and listen exactly once.** Almost every stream bug is really a
question about ownership: two pieces of code both thought they were the listener. If a value is
needed in two places, listen once and hand the value on — do not hand the *stream* on and hope.

**Prefer `await for` to `listen` when you are in a position to wait.** `await for` gives you a
loop, the study-20 `try` you already know, and cancellation when you leave it. `listen` gives
you a subscription and a callback, and you own the cancelling. Reach for it when there is no
function that can afford to sit in a loop.

And read the return type. `Future<List<int>>` says every value, once they are all in.
`Stream<int>` says one at a time, starting now, for as long as it goes on. Those are different
programs, and the type is where the difference is written down.
</Practice>

## Wrapping up

A `Stream<T>` is many values over time. `async*` makes a function that returns one, `yield`
sends a value, `yield*` sends every value of another stream, and `await for` reads them one at a
time. Nothing in the generator runs until something listens, and leaving the loop cancels it.

The verbs are study 12's and the waiting is study 21's. The genuinely new rule is that there is
one pass: a single-subscription stream is a `StateError` the second time, a broadcast stream is
a silent zero, and a `List` is what you want if you need to go round twice.

Also met: `sync*` against `async*`, `Stream.fromIterable`, `asBroadcastStream`, and an error
that ends a loop rather than a value.

That closes Book I. You have the whole language a program needs: values, types, flow,
functions, collections, patterns, objects, generics, failure and time. Book II starts putting
it in files — libraries, imports, privacy, and a package somebody else can use.
