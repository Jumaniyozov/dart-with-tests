## 20.1 Throwing

`throw` takes an object and leaves. Two things about it are worth naming now, because both are
already on the page above.

**`throw` is an expression.** dart.dev is explicit: "you can throw exceptions in `=>`
statements, as well as anywhere else that allows expressions." That is why the last arm of
`penceFrom`'s switch can *be* a `throw` — a switch expression needs every arm to produce a
value, and an arm that never produces one is allowed because it never finishes.

**`Never` is the type of that.** `noAmount` says so in its signature: it takes a string and has
no return type in the ordinary sense, because it does not return. `Never` sits below every type
in the language, so a call to it fits wherever any value is wanted — which is how
`value ?? noAmount(typed)` is an `int` and not an `int?`.

<include cwd lang="dart" meta='title="test/till_test.dart"'>../code/ch20_till/test/till_test.dart#refusing</include>

`FormatException` takes a message *and the source that caused it*, and the test above reads
that source back. An exception that only says "bad input" makes the caller go and find the
input again.

<Gloss title="int.tryParse is not a validator">
`wholeIn` checks that every character is a digit *before* it parses anything, which looks like
belt and braces until you see what `int.tryParse` accepts on its own:

Surrounding spaces are trimmed. A leading `+` or `-` is taken. And `'0x10'` is **sixteen**,
because `tryParse` reads hexadecimal — so a till leaning on `tryParse` alone would charge £16
for four characters nobody meant as a number.

"It returned non-null" and "the text was a number" are different claims. When the exact
characters matter, check them, and parse only what survives.
</Gloss>

## 20.2 Which of `Error` and `Exception` you mean

You can throw any non-null object in Dart. Do not. dart.dev's rule is one line —
"production-quality code usually throws types that implement `Error` or `Exception`" — and the
choice between those two is the real decision.

**An `Error` means the program is wrong.** `ArgumentError`, `StateError`, `RangeError`: someone
called something with what it plainly said it would not take. The fix is to change the code, so
catching one is nearly always a mistake — you would be papering over a bug.

**An `Exception` means the world is wrong.** The text was not a number, the file is not there,
the connection dropped. The code is fine and the situation is not. These are meant to be
caught.

The two are separate hierarchies, not one inside the other:

<include cwd lang="dart" meta='title="test/till_test.dart"'>../code/ch20_till/test/till_test.dart#kinds</include>

`ArgumentError` is not an `Exception`, and `FormatException` is not an `Error`. So `on
Exception` really does mean "the situations I expected", and it will not quietly swallow a bug.

Most of the time the type you want already exists. `FormatException` says "this text is wrong"
better than anything you would write. Define your own when the caller needs to catch *this*
failure and not others, or needs data off it that no existing type carries:

That is the whole justification, and it is a smaller one than most codebases act on. A
`BadLine` exists because "which line" is a fact `FormatException` has nowhere to put.

## 20.3 Catching

`try` runs the risky part. `on` filters by type. `catch` gives you the object, and a second
parameter gives you the stack trace. `on FormatException { … }` with no `catch` is the form to
reach for when you do not need the object — it says you handled a kind of failure, not that you
looked at one.

Here is the same failure answered two ways:

<include cwd lang="dart" meta='title="lib/till.dart"'>../code/ch20_till/lib/till.dart#skipping</include>

<include cwd lang="dart" meta='title="test/till_test.dart"'>../code/ch20_till/test/till_test.dart#answers</include>

Neither is the correct one. Stopping is right for a till, where a wrong total is worse than no
total; skipping is right for a log file you are summarising. What the language gives you is the
choice, stated in the code where a reader can see it.

Notice what `totalOf` does inside its `on` clause: it throws something *else*. That is a
deliberate trade and 20.4 gives it a price — a new exception starts a new stack trace, so the
line inside `penceFrom` that refused the text is lost. It is worth it here, because what
replaces it is the line number, which is what the caller actually needs. It is not worth it
when the new exception says nothing the old one did not.

**Order matters, because the first clause that matches wins.** dart.dev: "the first `catch`
clause that matches the thrown object's type handles the exception." Put the general one first
and the specific one below it is unreachable:

```dart title="lib/ordered.dart"
import 'till.dart';

int total(List<String> lines) {
  try {
    return totalOf(lines);
  } on Exception {
    return 0;
  } on BadLine {
    return -1;
  }
}
```

## 20.4 `finally`, `rethrow`, and two ways to lose the evidence

`finally` runs on the way out, whichever way out that is.

<include cwd lang="dart" meta='title="lib/till.dart"'>../code/ch20_till/lib/till.dart#logged</include>

<include cwd lang="dart" meta='title="test/till_test.dart"'>../code/ch20_till/test/till_test.dart#order</include>

Read the second test. The exception still reaches the caller — `finally` does not handle
anything, it just runs — and `'done twelve'` is in the log before the caller ever hears about
the failure. That is what `finally` is for: closing the thing you opened, on both paths, without
pretending to have fixed anything.

Now the third test, which is the one to be afraid of. A `return` inside `finally` does not just
leave early: it **replaces the exception with a return value**, and the failure is gone. Not
handled, not logged, not rethrown. Gone.

```dart title="lib/swallowed.dart"
import 'till.dart';

int hidden(String typed) {
  try {
    return penceFrom(typed);
  } catch (error) {}
  return 0;
}

int lost(String typed) {
  try {
    return penceFrom(typed);
  } finally {
    return 0;
  }
}
```

Both are on in this book, and both are pointing at the same habit: making a failure stop being

The second way to lose evidence is quieter, because the code looks like it is doing the right
thing:

```dart title="lib/copied.dart"
import 'till.dart';

int logged(String typed, List<String> log) {
  try {
    return penceFrom(typed);
  } on FormatException catch (error) {
    log.add('refused $typed');
    throw error;
  }
}
```

<Practice source="dart.dev — Error handling" href="https://dart.dev/language/error-handling">
Three of this study's rules are lints, and all three ship in `package:lints` and are therefore
already on in every package in this book — `empty_catches` from `core.yaml`,
`control_flow_in_finally` and `use_rethrow_when_possible` from `recommended.yaml`. You do not
have to remember them. You have to not switch them off.

The rule that is not a lint is the one worth carrying: **decide who is wrong before you decide
what to throw.** If the caller could not have avoided it, it is an `Exception` and somebody
should catch it. If the caller broke a rule you wrote down, it is an `Error` and nobody should
catch it — the failure is the point, because it makes a bug loud in development instead of
quiet in production.

And catch the narrowest type you can name. `on FormatException` says what you were expecting.
A bare `catch` says you were expecting anything, which includes the `Error` that means your own
code is broken, and turns it into a shrug.
</Practice>

## Wrapping up

`throw` is an expression, so it fits in a `=>` body or a switch arm, and `Never` is the type of
a function that only ever throws. An `Error` says the program is wrong and should not be
caught; an `Exception` says the world is wrong and should be. `try` / `on` / `catch` /
`finally` decides what happens next, first matching clause wins, and `finally` runs both ways
out without handling anything.

Two habits destroy the information you will need at three in the morning: a `catch` that does
nothing, and `throw error` where `rethrow` belonged. The analyzer names both. Believe it.

Also met: `FormatException`, `ArgumentError`, `StateError`, defining an exception type, and the
stack trace as a value you can read.

Studies 21 and 22 ask the same questions again about work that has not finished yet — where the
failure arrives after the function that caused it has already returned.
