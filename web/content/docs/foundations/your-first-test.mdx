A test is a small program that runs your code and checks the answer. You do not need to
finish this book to write one. You need a function and an expectation.

Dart ships the runner as a package called `test`. Add it to your project:

```bash
dart pub add dev:test
```

`dev:` puts it under `dev_dependencies`, which means it ships with your source but not
with your program. Tests live in a `test/` directory in files whose names end in
`_test.dart`. That naming is not a convention you can ignore: the runner finds tests by
it.

## 2.1 Write the test first

Writing the test first sounds backwards. It is not. The test states what you want in a
form the machine can check, and from that moment the analyzer and the runner are working
for you, telling you one step at a time what is missing.

`{String language = 'English'}` is a **named parameter with a default**: callers write
`hello('Elodie', language: 'Spanish')`, and callers who do not care about language write
nothing. `switch` used as an expression hands back a value; `_` is the case that matches
anything else.

<Gloss title="The language is the wrong type here">
Nothing stops you writing `hello('Elodie', language: 'Klingon')`. It compiles, it runs,
and it silently gives you English. A `String` accepts every string, and only three of
them mean anything. Study 6 replaces this with an enum, which makes the mistake
impossible instead of merely wrong. Notice the discomfort now; it is the feeling that
tells you a type is too loose.
</Gloss>

<Practice>
Name a test after the behaviour, not after the function. `greets by name` tells you what
broke when the line goes red; `test hello` tells you nothing the file name did not already
say. Read your test names on their own: they should form a description of the program.

Give each test one reason to fail. Several `expect` calls are fine when they check one
idea together — an empty name and a blank name are the same idea — but two separate ideas
in one test means the second one stops being checked the moment the first breaks.
</Practice>

## Wrapping up

You wrote a test before the code, read a compile error that named exactly what was
missing, made it pass with the smallest thing that could work, and refactored with the
test holding you steady. That loop is the rest of this book.

Also met: `test` and `expect`, `String`, `=>`, string interpolation, `const`, named
parameters with defaults, and `switch` as an expression.
