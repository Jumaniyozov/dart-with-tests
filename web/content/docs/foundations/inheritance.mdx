## 16.1 Saying it once

`class const Payment(super.pence, final String to) extends Entry {}` is a whole class, body and
all, in one line. Three things are happening in it.

**`extends Entry`** makes `Payment` an `Entry`. Not merely similar — a `Payment` can be passed,
stored and returned anywhere an `Entry` is wanted, which is why `balanceOf` takes a
`List<Entry>` and receives whatever mixture you like.

**`super.pence`** is a **super parameter**: take an argument here and hand it straight to the
parent's constructor. The longhand names the parameter, passes it, and declares it — three times for one value — and
the analyzer would rather you did not:

```dart title="lib/longhand.dart"
class Note {
  final String text;

  const new(this.text);
}

class Reminder extends Note {
  final int hour;

  const new(String text, this.hour) : super(text);
}
```

**`final String to`** adds a field only `Payment` has. Study 15's rules are unchanged: `final`
makes it a field, `const` before the name makes the constructor constant.

`pence` and `isDebit` are written once, in `Entry`, and all three classes have them — which is
what lets a function take the whole family at once:

## 16.2 The compiler counts the family

`sealed` is the word that pays study 14's promise. It says the subtypes of `Entry` are exactly
the ones in this file, and because the compiler can count them it can check a switch:

<include cwd lang="dart" meta='title="lib/entries.dart"'>../code/ch16_entries/lib/entries.dart#describe</include>

`Payment(:final to)` is an **object pattern**. It matches when the value is a `Payment` and, in
the same breath, pulls out the field named `to` and calls it `to`. `:final to` is shorthand for
`to: final to` — the field name and the variable name are usually the same, so Dart lets you
write it once.

There is no `default`, and there must not be. Delete a case:

```dart title="lib/incomplete.dart"
String describe(Entry entry) => switch (entry) {
  Payment(:final to) => 'paid $to',
  Refund(:final from) => 'refund from $from',
};
```

`Interest()` by name, exactly as study 14's records were named. Add a fourth kind of entry and
every switch that has not been told about it stops compiling — which is the entire reason to
seal a family rather than leave it open.

Guards work here too, and the rule study 14 measured over records holds over classes as well. Take
the unguarded `Payment()` away and leave only the guarded one:

```dart title="lib/guarded.dart"
int handlingFee(Entry entry) => switch (entry) {
  Payment(:final to) when to == 'self' => 0,
  Refund() => 0,
  Interest() => 50,
};
```

## 16.3 What `sealed` costs

Two things follow from sealing a family, and the second is a real price.

A `sealed` class is **abstract**: it has no instances of its own. `Entry(100)` is not an entry,
it is a mistake, because an entry is one of the three concrete kinds.

And nobody outside the file can join the family — including your own tests:

```dart title="lib/closed.dart"
import 'entries.dart';

/// A stand-in for a test. Every real project wants one of these.
class FakeEntry implements Entry {
  @override
  final int pence = 0;

  @override
  bool get isDebit => false;
}

/// And an Entry that is not any of the three.
final plain = Entry(100);
```

`implements` is the other way to take on a type. Where `extends` inherits the parent's
implementation, `implements` takes only its **interface** — the list of members you must
provide — and gives you nothing. `FakeEntry` has to write `pence` and `isDebit` itself, which is
exactly what a test double wants: the same shape, none of the behaviour.

`sealed` forbids it. That is the trade, stated plainly: exhaustive switching in exchange for a
closed family. (For `implements` succeeding, look ahead one section: `class F implements
Interface {}` is one of the two lines in 16.4 that produce no error.) It is the right trade for a ledger entry, which really is one of three things.
It is the wrong trade for a type other people are meant to extend.

## 16.4 Four modifiers, one sentence each

Dart lets you choose exactly how open a class is. Here is every modifier misused from another
library at once:

```dart title="lib/modifiers.dart"
import 'kinds.dart'; // sealed Sealed, final Final, base Base, interface Interface

class A extends Sealed {}

class B extends Final {}

class C implements Final {}

class D implements Base {}

class E extends Interface {}

// These two are fine.
class F implements Interface {}

base class G extends Base {}
```

Read the errors and the two silences together and the whole system falls out:

| Modifier | Outside its library you may | The point |
| --- | --- | --- |
| *(none)* | extend and implement | the default, and the most open |
| `interface` | implement only | a contract, not a starting point |
| `base` | extend only, and your class must be `base`, `final` or `sealed` too | the implementation is guaranteed to be inherited |
| `final` | neither | the hierarchy is closed, but you may add subtypes later |
| `sealed` | neither, and it is abstract | the compiler can count the subtypes |

`base` is the fiddly one: `D implements Base` fails twice over, once because a `base` class
cannot be implemented from outside and once because any subtype of it must carry a modifier
that keeps the guarantee going.

<Practice source="dart.dev — Class modifiers" href="https://dart.dev/language/class-modifiers#sealed">
dart.dev states the choice in one pair of sentences, and it is the whole decision:

**"To create a known, enumerable set of subtypes, use the `sealed` modifier."** And then:
**"If you don't want exhaustive switching, or want to be able to add subtypes later without
breaking the API, use the `final` modifier."**

Read that second sentence as the warning it is. Sealing is not a way of being careful, it is a
promise that the list is complete — and it is a promise to everyone who imports you, because
adding a fourth subtype later breaks every switch they have written. That is a *feature* inside
one program and a broken release for a published package.

The default remains the right choice more often than the modifiers do. Reach for `sealed` when
the family really is finite and you want the compiler to enforce it, as a ledger entry is.
Reach for `final` when you simply do not want strangers in your hierarchy. Leave a class plain
when you have no particular opinion — which is most of the time.
</Practice>

## Wrapping up

`extends` inherits a parent's fields and implementation, and `super.pence` hands a constructor
argument straight through. `implements` takes the interface and none of the behaviour, which is
what a test double wants. `abstract` means no instances of its own.

`sealed` is abstract plus closed, and closed is what lets the compiler count the subtypes and
check a switch — the guarantee study 14 promised, now over classes. The price is that nobody,
including your tests, can join the family from outside.

Also met: object patterns, super parameters, the `base` / `interface` / `final` modifiers, and
enums carrying fields, methods and statics.
