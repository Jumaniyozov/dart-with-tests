Foundations

Chapter 1

Meet Dart

Before syntax, a mental model: what Dart is, the three ways it compiles, and how to run a program — in this page or on your machine.

1.1 What Dart is #

Dart is a client-optimized, object-oriented language from Google with a sound, static type system. Two phrases there carry weight, and we'll unpack both across this book:

  • Object-oriented — every value is an object, an instance of some class. Even an int, a bool, and a function are objects. There are no "primitives" sitting outside the type system the way there are in Java.
  • Sound static types — types are checked when you compile, and Dart guarantees a value can never silently be a different type than its declaration says. (There's a precise nuance to "sound" — §2.6.)

You almost never have to write the types, though, because of pervasive type inference — the analyzer figures them out. So Dart reads as cleanly as a dynamic language while giving you the safety of a static one.

1.2 One language, three ways to run #

Dart's defining trait is that the same source targets very different runtimes. You don't need this on day one, but it explains why Dart exists:

ModeWhat it doesUsed for
JITJust-in-time compile while developing, with a fast dev loopdart run during development; hot reload
AOTAhead-of-time compile to native machine codeFast standalone CLI tools & apps (dart compile exe)
WebCompile to JavaScript or WebAssemblyRunning Dart in a browser

This book lives mostly in the first two. The browser detail matters for one reason you'll meet in §3.1: integers behave slightly differently on the web, because there they ride on JavaScript's number type.

1.3 Your first program #

Every Dart program begins at a top-level function named main. Run the program and Dart finds main and executes its body, statement by statement.

Decoding it: void is the return type (this function returns nothing); main is the entry point; () holds parameters (none here); { } wraps the body; print(...) is a built-in from dart:core; 'Hello, Dart!' is a String; and the ; ends the statement. Dart is case-sensitive and statement-terminated — a missing semicolon is the most common first error.

▶ Try it

Hit ▶ run in lab above, then press Run in the editor. Change the message, run again. That editor is the real Dart compiler — everything in this book runs there.

When you install the SDK (Chapter 28 covers setup), you get one command — dart — that does everything. The ones worth knowing now:

2.1 Declaring variables #

A variable is a name bound to a value. You can write the type, or let Dart infer it:

Verified detail

Inference uses the initializer only. var x = 3; makes x an int forever; a later x = 4.0; is an error. Subsequent assignments are never taken into account. (dart.dev/language/type-system)

2.2 var vs final vs const #

Three ways to bind, differing in when the value is fixed:

KeywordReassignable?When is the value known?Reach for it when…
varYesRuntimeThe binding genuinely needs to change
finalNo (set once)RuntimeDefault choice. Computed once, then stable
constNoCompile timeA true constant: literals, 3.14, Duration(seconds: 1)

A subtle superpower: two const values that are equal are canonicalized — they're the exact same object in memory. const [1,2] written twice is one shared instance.

Best practice — Effective Dart

Prefer final (or const) over var for locals you don't reassign. Immutability-by-default removes a whole class of "who changed this?" bugs and reads as intent.

2.3 The type hierarchy #

Every type sits in a single tree. Under sound null safety, the top type — the one that can hold anything — is Object?:

Two facts that trip people up: under null safety Null is no longer a subtype of Object (that's why Object? became the new top), and Never is the type with no values — the return type of a function that always throws.

2.4 dynamic, Object?, void & Never #

Four "any/none" types that beginners conflate. They are different tools:

TypeMeaningType checkingUse when
Object?Any value at all (incl. null)Checked — you must test/cast before using membersYou accept anything but want safety
ObjectAny non-null valueCheckedAnything except null
dynamicAny value, checks disabledDeferred to runtime — any member call compilesRare: interop, truly untyped JSON before parsing
void"Don't use the result"—Return type of functions called for effect
NeverNo value ever—A function that always throws / never returns

Gotcha

dynamic turns off the type checker for that value — it's a loaded gun. Prefer Object? + an is check, which keeps you safe. Reach for dynamic only when you genuinely can't know the type until runtime.

2.5 What "sound" really means #

Dart's type system is sound: a value can never silently mismatch its static type. But "sound" here has a precise meaning that surprises people coming from Haskell or Rust:

  • Soundness is upheld by a mix of compile-time checks and, where needed, inserted runtime checks.
  • A bad downcast or an illegal write through a covariant generic doesn't corrupt memory — it throws a TypeError at runtime.

Verified nuance (the one non-unanimous finding)

"Sound" means no silent heap pollution — mismatches throw. It does not mean "a typed program can never throw a type error." Academic work calls Dart "unsound" under that stricter definition. Practically: runtime TypeErrors are still possible, usually from as casts or dynamic. (dart.dev/language/type-system)

Check yourself

You read JSON into a variable and don't yet know its shape. Which type keeps the most safety while still accepting anything?

Both dynamic and Object? hold anything, but Object? keeps the type checker on — you can't call a member until you've tested the type. That safety is exactly what you want around untrusted data. dynamic would let a typo compile and crash at runtime.

A record groups a fixed number of values, each possibly a different type, into one value. Records are anonymous (no class needed), immutable, and have value equality (two records with equal fields are equal).

8.3 Laziness — the big gotcha #

Most Iterable methods are lazy: map and where don't do any work when you call them. They build a recipe; the work happens only when you iterate (a for loop, toList(), first…). This has two consequences that bite beginners:

Two lazy traps

(1) Side effects in map won't happen until you iterate. (2) A lazy Iterable re-computes every time you read it — so if you'll use the result more than once, call .toList() to compute it once and cache it.

You write var r = list.map(expensive); and then read r.length, r.first, and loop over r. How many times does expensive run per element?

A lazy Iterable recomputes on every iteration. .length, .first, and the loop each trigger the pipeline. Add .toList() once and read that if you need the values repeatedly.

Null Safety

Dart's defining safety feature deserves its own part. Master the difference between "a value" and "maybe no value," and the small set of operators that make working with absence painless.

Chapter 12

Sound null safety in depth

Why a crash class vanished, how ? changes a type, the operators ?. ?? ??= !, and how the compiler "promotes" nullable values to non-null after a check.

12.1 Non-nullable by default #

Verified history

Sound null safety shipped stable (opt-in) in Dart 2.12 (March 3, 2021) and became unconditional in Dart 3.0. Variables can't hold null unless their type ends in ?. (dart.dev/language)

The payoff: the entire category of "null reference" crashes is moved from runtime surprise to compile-time error. The compiler simply won't let you use a possibly-null value as if it can't be null.

12.2 The null-aware operators #

OperatorMeaningExample
?.Call only if not null (else the whole expression is null)user?.name
??Use the right side if the left is nullname ?? 'guest'
??=Assign only if currently nullcache ??= compute()
!Assert non-null (throws if you're wrong)value!
?..Null-aware cascadebuilder?..a()..b()

Use ! sparingly

The bang ! is a promise to the compiler: "trust me, not null." If you're wrong, it throws a runtime error — re-introducing exactly the crash null safety prevents. Prefer ?., ??, or a real check. Reach for ! only when you can prove non-null but the compiler can't.

12.3 Flow analysis & promotion #

The compiler tracks your checks. After you've proven a nullable value isn't null, it's promoted to the non-null type for the rest of that scope — no ! needed:

Why promotion sometimes "doesn't work"

Promotion only applies to local variables (and final fields it can prove stable). A non-final instance field can't be promoted — between the check and the use, other code might change it. The fix: copy the field into a local first (final n = name; if (n != null) ...).

12.4 late — deferred non-null #

late says "this non-nullable variable will be assigned before it's read — just not right now." Useful for values set in init code, or expensive values you want computed lazily on first use:

The late bargain

late trades a compile-time guarantee for a runtime one: read it before it's assigned and you get a LateInitializationError. It's a sharp tool — use it when you genuinely can't initialize at declaration, not to dodge the type system.

Check yourself

A class has a non-final field String? title;. Inside a method you write if (title != null) print(title.length); and it won't compile. Best fix?

Non-final instance fields can't be promoted (another method could null it between check and use). Copying into a local t gives the analyzer a stable value it can promote. ! (A) compiles but re-opens the crash risk.

Chapter 17

Class modifiers & sealed types since 3.0

Dart 3 gives you precise control over how others can extend, implement, or mix in your classes — and sealed unlocks exhaustive switches that the compiler checks for you.

17.1 The six modifiers #

Verified

The modifiers before class are abstract, base, final, interface, sealed, and mixin. All except abstract require language version ≥ 3.0. (dart.dev/language/class-modifiers)

ModifierAllows others to…Use when

Verified — the base rule

Any class that extends or implements a base class must itself be marked base, final, or sealed. This stops outside libraries from breaking the base class's guarantees. final includes the effects of base. (dart.dev/language/class-modifiers)

17.2 Sealed classes & exhaustiveness #

A sealed class tells the compiler it knows every direct subtype (they must live in the same library). That makes a switch over them provably exhaustive — forget a case and your code won't compile.

Verified

Sealed classes are implicitly abstract (you can't construct them) and enable exhaustiveness checking over their subtypes. (dart.dev/language/class-modifiers, /branches)

Why this is a superpower

"Exhaustiveness" turns your type system into a checklist. When requirements grow (a new payment type), the compiler walks you to every place that must change. This is the single biggest reason to model fixed alternatives as sealed rather than loose strings or enums-without-data.

Check yourself

You model app screens as a sealed class Screen with subtypes Home, Profile, Settings, and switch over them without a default. A teammate adds Search extends Screen. What happens?

That's the whole value: adding a subtype to a sealed type breaks compilation at every exhaustive switch, so you can't forget to handle the new case. Compare to a default, which would silently swallow it.

An extension bolts new members onto an existing type — even a built-in like String or int — without subclassing it:

18.2 Extension types since 3.3 #

An extension type wraps an existing representation type with a different, static-only interface. It's a way to give a primitive a meaningful type (a "type-safe alias") without the runtime cost of a wrapper class.

Verified

Extension types are a compile-time abstraction, compiled away at run time with no trace, so they're essentially zero cost (no wrapper allocation). Unlike extension methods, they can define a new API that hides the underlying type. Released in Dart 3.3 (Feb 15, 2024). (dart.dev/language/extension-types)

Important caveat

Extension types are an unsafe abstraction: because they compile to the underlying type, the representation can be recovered at runtime (e.g. via dynamic). They give you compile-time safety and zero overhead, not airtight encapsulation. For true hiding, use a real class.

Chapter 20

Errors & exceptions

The difference between an Error and an Exception, how to throw and catch, and the judgment of when to recover versus let it crash.

20.1 Exception vs Error #

Dart has two families of throwable objects, and the distinction guides how you treat them:

TypeMeansYou should…
ExceptionA condition you can anticipate & recover from (bad input, network down, file missing)Catch and handle it
ErrorA programmer bug (null check failed, bad cast, out-of-range index, failed assert)Not catch it — fix the code

Best practice — Effective Dart

Throw Exceptions (or your own subtypes) for recoverable problems. Error and its subtypes signal bugs — don't catch them to "handle" the symptom; let them crash so you find and fix the cause.

20.2 throw, try / catch / on / finally #

Use on Type to catch a specific exception type, plain catch (e) for anything, and the second parameter (catch (e, stack)) to capture the StackTrace. finally runs whether or not an error occurred — ideal for releasing resources.

20.3 rethrow & custom exceptions #

Use rethrow, not throw e

Inside a catch, rethrow preserves the original stack trace. Writing throw e; instead resets the trace to this line, losing where the error really came from.

Check yourself

Your code does list[99] on a 3-element list and throws RangeError (a subtype of Error). Best response?

RangeError is an Error — it signals a bug in your logic. The right fix is to correct the index (or guard with a length check), not to catch and limp on, which hides the defect.

20.4 Error-handling patterns #

Beyond the mechanics, a handful of patterns separate robust code from fragile code:

Fail fast on bad state

The earlier a problem surfaces, the cheaper it is to fix. Validate inputs at the boundary and throw immediately, rather than letting bad data flow deep into the system where the eventual crash is far from the cause:

Recover, don't suppress

Catching an error to do something (retry, fall back, message the user) is good. Catching it to silence it — an empty catch block — is how bugs go invisible. If you can't handle it here, don't catch it here.

The empty-catch anti-pattern

try { risky(); } catch (_) {} swallows everything, including bugs you'd want to know about. If you must catch broadly, at least log it (below) and re-throw what you can't handle.

Clean up with finally

Throw vs. return a Result

A decision worth making consciously (revisiting §19.5): use a Result or nullable return for expected failures the caller should handle explicitly (parse / validate / not-found); reserve throwing for exceptional situations and programmer bugs. Throwing for ordinary control flow makes code hard to follow.

20.5 Debugging & logging #

When something does go wrong, these tools help you find out why:

ToolFor

Best practice

Prefer the debugger and structured log() over scattered prints. A logged error with its stack trace tells you where and why; a bare print('here') only tells you the line ran. Always log the StackTrace from catch (e, stack) — without it, you're guessing.

Chapter 21

Futures & async/await

Dart's single-threaded concurrency model, the event loop and its two queues, and how async/await let you write non-blocking code that reads top-to-bottom.

21.1 The model: one thread, an event loop #

A Dart isolate (Chapter 23) runs on a single thread. It never blocks waiting; instead an event loop pulls work from two queues. Understanding the order is the key to predicting async behavior:

  • Microtask queue — tiny internal tasks (e.g. completing a Future). Drained completely first.
  • Event queue — external events (timers, I/O, user input). One is processed only when the microtask queue is empty.

21.2 Futures & async/await #

A Future<T> is a promise of a T that will arrive later (or an error). await suspends the function until it completes, then resumes with the value — without blocking the thread:

Two classic mistakes

(1) await only works inside an async function. (2) Forgetting await gives you the Future object instead of the value — and silently swallows its errors. The unawaited_futures lint catches this.

Chapter 23

Isolates & concurrency

Async keeps one thread responsive but doesn't add CPU. For genuinely parallel, heavy work, Dart gives you isolates — workers that share no memory and communicate by messages.

23.1 Why isolates (vs threads) #

async/await interleaves tasks on one thread — perfect for I/O, useless for a long calculation that would freeze that thread. For that you need true parallelism: an isolate.

Verified — the model

All Dart code runs inside an isolate. Each isolate has its own memory and event loop; none of an isolate's state is accessible from another. So there's no shared mutable state — and therefore none of the data-race bugs that plague threads. Isolates communicate only by passing messages. (dart.dev/language/concurrency)

23.2 Isolate.run — the easy way #

For "do this expensive thing off the main thread and give me the result," Isolate.run is all you need. It spawns an isolate, runs your function, returns the result as a Future, and shuts down:

Best practice

Use isolates only for CPU-bound work (parsing huge JSON, image processing, crypto, heavy math). For I/O (files, network), plain async/await is already non-blocking — an isolate would just add overhead.

23.3 Long-lived isolates: ports #

For a worker you talk to repeatedly, spawn it with Isolate.spawn and exchange messages over a SendPort/ReceivePort pair. The data you send is copied (since nothing is shared):

What can cross between isolates

Messages must be copyable: primitives, strings, lists/maps of those, and most simple objects. You can't share a mutable object reference — the receiver gets a copy. That copy cost is why you send compact data and do the heavy work inside the isolate.

Check yourself

Your app downloads a file (network I/O) and the UI stutters. Reach for…?

I/O doesn't burn CPU — await already frees the thread while waiting. Isolates are for CPU-bound work. If a download stutters the UI, the culprit is usually heavy processing of the result (parse/decode), and that step is what belongs in Isolate.run.

30.3 Effective Dart — the digest #

Verified structure

Effective Dart is four guides — Style, Documentation, Usage, and Design — under one overarching theme: be consistent. Guidelines are graded DO / DON'T / PREFER / AVOID / CONSIDER. (dart.dev/effective-dart)

Style — naming & layout

  • UpperCamelCase for types & extensions; lowerCamelCase for members, variables & parameters; lowercase_with_underscores for files & packages.
  • Capitalize acronyms longer than two letters like words: HttpRequest, IOStream (not HTTPRequest).
  • Let dart format own all whitespace — never hand-format.

Documentation

  • Use /// doc comments for public APIs; start with a single-sentence summary.
  • Write doc comments as prose for a reader, and reference identifiers in [square brackets].

Usage

  • PREFER interpolation over +; use adjacent strings to concatenate literals; omit braces for simple $id.
  • DO use collection literals ([], {}) and collection-if/for instead of building then mutating.
  • DO use final for locals you don't reassign; AVOID var when you mean a constant.
  • Name boolean properties with a non-imperative verb phrase: isEmpty, hasElements, canClose.

Design

  • PREFER making fields and top-level variables final; design for immutability.
  • AVOID dynamic unless you truly need it; annotate where inference can't help a reader.
  • Use getters for property-like access (cheap, no side effects), methods for actions.
  • Throw Exceptions for recoverable failures; avoid throwing bare Error or String.
Check yourself

Types use UpperCamelCase, and acronyms longer than two letters are capitalized like ordinary words — so Http, not HTTP. Hence HttpRequest (the SDK itself follows this).

33.2 Metaprogramming: code generation #

33.4 Performance & memory notes #

  • Prefer const for values known at compile time — they're canonicalized (one shared instance) and free to create.
  • Don't prematurely optimize. Write clear code first; measure with the DevTools profiler before tuning.
  • Offload CPU-bound work to isolates (Ch 23) so the main thread stays responsive — but only for genuinely heavy compute.
  • Reuse buffers (StringBuffer, typed-data lists) in hot loops instead of allocating in each iteration.
  • Lazy Iterables (Ch 8) avoid building intermediate lists — but call .toList() once if you'll reuse the result.
  • AOT-compile for production (dart compile exe): faster startup and steady-state than the JIT.
